# Verification of RTL timing facts

Four layers check the facts against the compiler and against simulated hardware. None qualifies operations or configurations outside the extracted scope.

## Extractor tests

`test/test_rtl_extract_*.py` cover the interpreter, the coupled recipe and spec validation on synthetic circuits, and (with `ATLAS_HW_IR` and `ATLAS_HW_EXPORTER` set) reproduce every value in the [results table](README.md#results). Mutations such as an extra register stage or a payload-dependent control path must move or reject the result.

## Compiler cross-check

`test/test_rtl_extract_compiler.py` compares each extracted record with the compiler's built-in footprints (`lib/AtlasTiming.cpp`, via `test/rtl-timing-facts-probe.cpp`) and fails on any difference. `test/rtl-timing-facts-map.yaml` maps records to compiler mnemonics and states the conventions; every record is compared or listed as not modeled. This detects drift between the compiler's constants and the RTL. Commands are in the [extractor reference](../../tools/rtl_extract/README.md#compiler-cross-check).

`test/test_rtl_gap_coverage.py` checks pair sweeps the other way round: for every `rtl_extract.op_pairs.v1` record (`ATLAS_PAIR_SWEEPS`, default every `pairs-*.json` beside `ATLAS_OP_TIMING`; system pairs are mapped by decoding their instruction words and requiring the compiler to encode the same word), the smallest gap `--verify-atlas-rtl-timing` accepts must be at least the record's `stable_gap`. It prints the slack, and, for information, the built-in rules' gaps, which equal `stable_gap` for every swept pair except two MXU pairs where they are larger.

## Selected-mode tests

`test/test_rtl_timing.py` and, for MXU, `test_rtl_mxu_timing.py` run scheduling, delay insertion and `--verify-atlas-rtl-timing` with the facts selected, and check that wrong digests, a missing selection, unsupported domains, early or missing terminals and unsafe streams are rejected, and that admission numbers come from the facts rather than constants. Final verification rechecks timing from the actual instruction stream, also in `atlas-emit` and the LLVM handoff, so rewrites after scheduling cannot silently invalidate it.

`test/test_rtl_overlap.py` checks each admission rule at its boundary for every first/second combination of vload, vstore, VPU, XLU and MXU: accepted at the facts-derived gap and rejected one cycle earlier with the busy unit named, with both consumers issuing at that boundary.

## Simulation

**Compiler-scheduled programs on Verilator.** `tools/replay-ee290-compute.py --facts F.json --bin <dir with atlas-opt, atlas-emit> --work DIR (--model VAtlasCore | --rtl <dir of .sv/.v>)` runs every case in `tools/ee290_replay_cases/` (or `--cases a,b`) on AtlasCore with the facts selected and `dma=wait`, and prints `PASS <case>` or exits nonzero. A case is data: instructions, initial and expected VMEM/DRAM, and expected command counts; a new file in that package is discovered automatically. The model must be built with the current `test/ee290-compute-replay.cpp`, which loads a case image and checks every initialized byte. The validator follows the PC through branches with the one delay slot, requires every engine idle and no DMA pending at each block entry, tracks one live command per engine, and attributes every port event to its engine. `tools/check-ee290-compute-export.py` binds each dynamic block instance to the block-relative offsets of `atlas-emit --rtl-timing-json`, and each command's accesses (address and age) and release to its own footprint; holds on other engines may outlast the command but not end before it. Hand-scheduled cases (`final=True`) bind footprints to a delay-inserted reference instead of issue offsets. DMA completion is anchored to the matching wait, never to a latency. The cases cover transpose, BF16 multiply, DMA→transpose, a loop, a DMA loop, both arms of an if/else, and two overlap streams (vload with vstore on distinct banks one cycle apart; a VPU multiply with a vload one cycle later), where the hardware kept each command's isolated timing. Relaxation cases run the compiler's own overlapping schedules with both consumers and require the overlap to occur: vmul→vmul at 65 (the second issues on the edge of the first's last write, admitted by the RTL's issue-busy bit), vload/vstore on distinct banks at 1 and on one bank at exactly 30 and 34, a VPU under a vload at 1, and a pipelined load-transpose-store. The validator lets a second VPU command go live only when the first has issued all reads and received all responses and the new op's issue-busy bit is clear; the draining command keeps the remaining writes. Two cases run one FP8 tile through each MXU (weight push, overwrite matmul, BF16 pop; MXU1 on slot and accumulator 1): the validator checks weights and activations against their MREG rows and pops against the recorded accumulator, MXU busy is derived from the sequencer's port engines and in-flight tracker, and expected results come from an exact fixed-point reference. Accumulator writes landed at ages 63–94 (MXU0) and 3–34 (MXU1), as extracted. The replay decodes every VPU operation (binary, unary, row and column reductions, FP8 pack/unpack with the scale register read at issue, immediate loads) and checks written rows against exact lane references where one exists (relu, mov, max/min, immediate loads and pack/unpack bit for bit; add/sub, square/cube and sums only where exact; exp on special values and exp2 on integers); other transcendentals are rejected. MXU accumulator pushes (FP8 dequantized, BF16 pairs), accumulating matmuls (checked against the accumulator) and FP8 pops (scale register read at issue) run on both MXUs, and SELD binds to its VMEM read at age 1 and scale write at age 3. Several DMA commands may be pending on distinct channels: requests follow launch order, responses their TileLink source, and each completion precedes its own channel's wait; hand-scheduled streams bind to a reference in which each wait follows its launch. All new operations matched their facts ages; 51 runs pass. A vload and vstore on the same VMEM bank one cycle apart trips the RTL assertion "VLOAD and VSTORE target same VMEM bank". `test/test_ee290_compute_replay.py` runs it when `ATLAS_EE290_COMPUTE_MODEL`, `ATLAS_OOT_BIN_DIR` and `ATLAS_OP_TIMING` are set, and mutates saved traces to check rejections.

**Issue #11 VCS witness.** `tools/run-ee290-vls-witness.py --program test/examples/ee290_vls_copy.mlir --facts F --atlas-opt PATH --atlas-emit PATH --simulator simv --host-cc <riscv gcc> --output DIR [--schedule delay|schedule]` selects the facts, schedules or inserts delays, verifies, emits, builds the host program and runs `simv +loadmem`; it exits 0 on pass, 1 on a failed or license-unavailable run and 2 on a tool error. It checks outputs and guard memory, not event timing. Earlier Verilator and VCS waveform captures of the VLS copy kernel matched the compiler's predicted events cycle for cycle.

**DMA.** Simulation cannot bound external completion, so the `dma=wait` policy rests on structure: one pending transfer, VMEM exclusive until the matching wait, and verification that every launched transfer is waited before reuse, publication or halt.
