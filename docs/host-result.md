# Full-host result transport

New full-host builders can import `tools/chipyard/result_transport.py`, call `add_arguments(parser)` and call `write_config(out, args)` before compiling. Include its generated `atlas_result_transport.h` and the shared `runtime/atlas_result.h` in the host source; include the generator, shared header, generated header and returned transport metadata in the build's source and artifact bookends. Existing kernel, selected-layer and Tiny block builders are unchanged.

The full-host default is the EE290 SiFive UART at `0x10020000`. This address and `sifive,uart0` compatibility come from `sims/vcs/generated-src/chipyard.harness.TestHarness.EE290GenericIOSimConfig/chipyard.harness.TestHarness.EE290GenericIOSimConfig.dts` in the surrounding Chipyard workspace. Register offsets come from `generators/rocket-chip-blocks/src/main/scala/devices/uart/UARTCtrlRegs.scala`; `UART.scala` defines transmitter enable at bit zero of TXCTRL and `util/RegMapFIFO.scala` defines TXDATA bit31 as FIFO full. The generated sink enables transmission, polls FIFO full and performs volatile 32-bit MMIO writes. It preserves the hardware's baud divisor unless `--uart-divisor` is supplied; no clock or baud estimate is embedded.

Use `--uart-kind ns16550 --uart-base 0x10000000` for QEMU virt, which has a different UART from EE290. This generates byte MMIO accesses polling line-status bit5 and writing the transmit register; an explicit divisor updates DLL/DLM while preserving line-control settings. NS16550 requires an explicit base. The QEMU virt device tree declares `ns16550a` and address `0x10000000`; a diagnostic must capture QEMU's actual serial output using `-serial file:uart.log`. The two transports produce different ELF bytes and must be recorded as distinct artifacts. Neither a QEMU UART diagnostic nor a selected DTS proves a board has a matching UART connection or clock.

Initialize `atlas_result_uart uart; atlas_result result; atlas_result_uart_init(&uart);`, then call `atlas_result_begin(&result, atlas_result_uart_putchar, &uart, "model-name", expected_launches)`. Names, check identifiers and boundaries must be nonempty whitespace-free constants so the records remain parseable. After each completed and checked launch group, call `atlas_result_progress(&result, completed_launches, "layer-name")`; completed counts must increase and cannot exceed the expected count. Group progress permits bounded per-layer reporting without one line per physical launch.

Check the actual output and completion state with `atlas_result_check(&result, "check-name", observed, expected)`, or report a caller-detected error using `atlas_result_fail`. Failed checks are sticky. `atlas_result_pass` returns zero and emits no PASS if any check failed, the launch count is incomplete, the expected count is zero or completion repeats. Callers retain responsibility for their authenticated reference checks, traps and halt policy. A PASS record alone cannot replace verification of actual output, complete launch order and frontend termination.

Records retain the existing `ATLAS_KERNEL_` prefix with BEGIN, PROGRESS, FAIL and PASS suffixes, name and explicit completed/expected launch counts. FAIL includes check, observed and expected values. UART output has no HTIF dependency; a caller can separately retain HTIF termination for FireSim or remain halted with observable UART status on a board. A physical UART with an incorrect address or unavailable transmitter can block while polling; the image owner must provide the matching map and external run timeout.

Focused host tests compile the C state machine and check sticky corruption, missing launches, duplicate progress and empty workloads, plus transport option validation. A separate freestanding RV64 diagnostic under QEMU virt exercises actual UART MMIO with positive BEGIN/PROGRESS/PASS and a forced bad-byte BEGIN/PROGRESS/FAIL, without HTIF or an accelerator. This establishes result transport and failure observability in QEMU; it does not establish Atlas numerics, SoC timing, board execution or FPGA loader correctness.
